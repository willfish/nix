Design Tool and MCP Boundaries

A model should not "do" business actions. It should request well-defined operations through contracts that application code owns, validates, observes, and can deny.

The Win

You will define one safe read tool, one risky write tool, and decide whether either belongs behind an MCP server.

Primary Sources

  • OpenAI Function calling for tool schema design and strict structured arguments.
  • MCP introduction for connecting AI applications to tools, data, and workflows through a shared protocol.
  • MCP specification for authoritative client/server concepts.

Boundary Rules

Arguments are contracts

Use precise schemas, enums, required fields, and narrow types. The model chooses arguments; application code validates them.

Effects are explicit

Separate read-only tools from tools that mutate, spend money, expose data, notify users, or change external state.

MCP is a boundary

Use MCP when the same data or tool surface should be reusable across AI clients, agents, editors, or workflows.

Example Contract

{
  "name": "create_refund_case",
  "description": "Create a pending refund case for human review.",
  "strict": true,
  "parameters": {
    "type": "object",
    "required": ["order_id", "reason", "risk_level"],
    "properties": {
      "order_id": { "type": "string" },
      "reason": { "type": "string", "maxLength": 500 },
      "risk_level": { "type": "string", "enum": ["low", "medium", "high"] }
    },
    "additionalProperties": false
  }
}
